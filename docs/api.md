# Реализованный API

Источник требований — [spec.md](../spec.md). TypeScript-интерфейс подключён к маршрутам авторизации и профиля. API заявок реализован; подключение интерфейса заявок к нему остаётся отдельной задачей.

## Авторизация

- `POST /api/auth/login`: JSON `{"email":"student@mukpid.example","password":"..."}`. Email приводится к нижнему регистру. Ответ 200: `{"data":{"authenticated":true}}`. JWT приходит только через Set-Cookie, не в теле ответа.
- `POST /api/auth/logout`: 204 без тела; отзыв текущей серверной сессии и очистка cookie. Повторный выход допустим.
- `GET /api/auth/me`: `{"data":{"id":"uuid","email":"...","role":"student","fullName":"...","faculty":"...","department":null,"program":"...","year":1,"groupName":"..."}}`. У преподавателя без группы program/year/groupName равны null; department содержит кафедру. Старый /api/me удалён.
- `GET /health`: `{"status":"ok"}`, не проверяет PostgreSQL.

JWT: HS256, issuer mukpid-api, audience mukpid-web, sub — ID пользователя, jti — случайный идентификатор сессии. Проверяются подпись, обязательные claims, срок, совпадение пользователя и действующей сессии. Роль берётся из базы. В sessions.token_hash хранится SHA-256 от jti, не JWT. Срок 8 часов без продления. Новый успешный вход отзывает прежнюю сессию из cookie браузера. Cookie: session локально, __Host-session в production; HttpOnly, SameSite=Lax, Path=/, Secure в production.

Для POST нужен `X-CSRF-Protection: 1`, для JSON — Content-Type: application/json. Origin должен совпадать с APP_ORIGIN (по умолчанию http://localhost:5173). Фронтенд использует относительные URL и proxy /api. CORS не включён; запросы cross-site запрещены.

Веб-клиент при загрузке вызывает `/api/auth/me`, после входа получает профиль повторно и хранит его только в памяти страницы. Cookie управляется браузером. Выход вызывает `/api/auth/logout` и очищает клиентский профиль только после успешного ответа. В локальной разработке Vite проксирует `/api` на `http://127.0.0.1:3001`; открывать интерфейс следует через `http://localhost:5173` при стандартном APP_ORIGIN. Для собранного сайта нужен сервер с маршрутизацией `/api` на бэкенд с того же origin.

Ошибки имеют вид `{"error":{"code":"UNAUTHORIZED","message":"Войдите в аккаунт"}}`. 400 BAD_REQUEST — невалидный ввод; 401 INVALID_CREDENTIALS — неверные реквизиты; 401 UNAUTHORIZED — отсутствующая, поддельная, истёкшая или отозванная авторизация; 403 FORBIDDEN — CSRF; 429 RATE_LIMITED — больше 10 попыток входа в минуту с IP. Лимит в памяти процесса. Ответы не кешируются.

## Окружение и демоданные

JWT_SECRET — случайный секрет минимум 32 байта, только в окружении. Production требует NODE_ENV=production и HTTPS APP_ORIGIN. Смена JWT_SECRET инвалидирует все ранее выданные JWT.

Демо email: student@mukpid.example, student2@mukpid.example, teacher@mukpid.example. При создании пароли берутся из SEED_STUDENT_1_PASSWORD, SEED_STUDENT_2_PASSWORD, SEED_TEACHER_PASSWORD в .env. Уже существующим пользователям seed не меняет пароль и не требует его повторно; пустая переменная не означает пустой пароль в базе. Пароль demo123 из макета не используется сервером.

Если демонстрационные студенты уже существовали до заполнения переменных, локальная команда `npm run db:reset-demo-passwords` задаёт им пароли из `SEED_STUDENT_1_PASSWORD` и `SEED_STUDENT_2_PASSWORD` (минимум 12 символов). Команда требует обе записи с ролью student, обновляет только их и отзывает их сессии. В production она запрещена; пароли не печатаются.

Для существующего демонстрационного преподавателя локальная команда `npm run db:reset-demo-teacher-password` задаёт пароль из `SEED_TEACHER_PASSWORD` (минимум 12 символов). Она требует запись `teacher@mukpid.example` с ролью teacher, обновляет только её и отзывает её сессии. В production команда запрещена; пароль не печатается.

## Миграция и границы реализации

Миграция 0001 переименовывает students в users с сохранением ID, паролей и связей. Старые login student1/student2 преобразуются в указанные email; иные логины без @ — в <uuid>@legacy.example. Добавлены роли, faculty и department; group_id допускает null для преподавателя. Сессии ссылаются на user_id. Старые cookie перестают работать после перехода на JWT.

Расписание, оценки, уведомления, ведомости и обращения пока не реализованы как API. Их старые таблицы ещё нуждаются в адаптации. Интерфейс для этих разделов использует локальные фиктивные данные, разделённые по ID вошедшего пользователя в localStorage; они не являются серверными данными и не обеспечивают синхронизацию между устройствами. Очистка истёкших сессий пока не автоматизирована.

Текущие часы и дата в интерфейсе берутся из устройства и обновляются на открытой странице. Исторические демособытия имеют абсолютные даты 2026 года; это не время сервера и не данные расписания из API.


## Заявки

После обновления выполнить `npm run db:migrate` (миграция 0002). Добавлены `purpose`, `delivery`, статусы `issued` и `cancelled`; старые записи сохраняются, для них purpose пустая и delivery=office. Старые неизвестные типы заявок требуют отдельной миграции данных; автоматического преобразования или удаления нет.

Все маршруты требуют действующий JWT и сессию студента. Владелец берётся из базы, переданный клиентом studentId не используется. Преподавателю возвращается 403.

- `GET /api/requests` → `{data: [...]}`, собственные записи, новые первыми.
- `POST /api/requests` → 201 `{data: {...}}`. Тело: `{type: "study", purpose: "По месту требования", comment: "", delivery: "pdf"}`. type: study/order/leave/retake, purpose: 1–500 символов, comment: до 2000, delivery: pdf/office. Цель и комментарий обрезаются по краям; пустая цель запрещена. Статус новой заявки submitted. Одновременно создаётся персональное уведомление в БД; лента уведомлений фронтенда пока не читает его.
- `PATCH /api/requests/:id/cancel` без тела → 200 `{data: {...}}`. submitted/in_progress → cancelled, повтор допустим. Чужая запись: 403; отсутствующая: 404; ready/issued/rejected: 409; неверный UUID: 400. Изменение проверяет статус и владельца в SQL.

Запись ответа содержит id, studentId, type, purpose, comment, delivery, status, createdAt и updatedAt (ISO). При изменении нужны `X-CSRF-Protection: 1`; JSON Content-Type нужен только при передаче тела.

API не импортирует браузерные демозаявки в базу. Клиентское хранение заявок и фильтры будут заменены при подключении интерфейса к API. Отменённые и отклонённые записи остаются в серверной истории. Обработка сотрудником и PDF описаны ниже.

Интеграционный сценарий `apps/api/tests/requests.test.ts` проверяет изоляцию двух студентов, роль преподавателя, сохранение, отмену, валидацию, CSRF и отзыв сессии. Он требует работающую PostgreSQL и применённые миграции.

Проверка 10 ноября: миграции с нуля и оба интеграционных теста прошли на отдельной временной PostgreSQL 17. Миграция локальной рабочей базы этим не подтверждается.


## Сотрудник деканата и PDF

Миграция 0003 добавляет роль staff и поля processedBy, readyAt, documentBase64. `documentBase64` не входит в JSON-ответы API. Сотрудник имеет доступ ко всем заявкам прототипа; разграничение по факультетам пока не реализовано. Демоаккаунт `staff@mukpid.example` создаётся командой `npm run db:seed`, пароль берётся из `SEED_STAFF_PASSWORD` (12+ символов). Существующие пароли не меняются.

- `GET /api/staff/requests` — только staff; список всех заявок с fullName и groupName студента.
- `PATCH /api/staff/requests/:id/status` — только staff, JSON `{status: "in_progress" | "ready" | "issued"}`. submitted → in_progress/ready, in_progress → ready, ready → issued; повтор текущего статуса допустим. Обратные переходы и изменение cancelled/rejected возвращают 409, отсутствующая запись — 404. При изменении обязателен CSRF-заголовок. Строка блокируется в транзакции; статус, сотрудник, время, PDF и уведомление записываются вместе.
- `GET /api/requests/:id/pdf` — только студент-владелец, delivery=pdf и статус ready/issued. Чужая заявка — 403, отсутствующая — 404, неготовый документ или office — 409.
- `GET /api/staff/requests/:id/pdf` — только staff, доступен готовый PDF независимо от способа получения. Формат ответа application/pdf с Content-Disposition: attachment. Скачивание не меняет статус.

PDF создаётся при ready и сохраняется в БД как снимок данных заявки и профиля. Шрифт с кириллицей и лицензия лежат в apps/api/assets; при переносе собранного API нужно переносить и каталог assets. Это демонстрационный бланк: для study справка об обучении, для остальных типов подтверждение обработки. Пометки о конкурсном концепте и вымышленных данных обязательны. Настоящие приказы, решения и юридически значимая подпись не формируются. Исторические ready/issued без сохранённого PDF недоступны для скачивания.

Кабинет `/staff` открывается после выбора вкладки «Сотрудник» при входе. Студенту добавлена кнопка обновления списка и скачивания готового PDF. Проверки переходов, изоляции PDF, неизменности файла при повторном скачивании и запретов для преподавателя включены в npm test.

После изменения SEED_STAFF_PASSWORD в .env выполните из корня `npm run db:reset-demo-staff-password`. Команда меняет пароль существующего демосотрудника и отзывает его сессии. Обычный seed пароль не меняет.


## Отличия от целевой обработки справки study

В spec.md определён следующий этап обработки справки об обучении. Пока не реализованы: проверка полноты учебных сведений и подтверждение факта обучения, отдельный черновик/предпросмотр, проверка актуальности снимка перед выпуском, обязательный порядок submitted → in_progress → ready для study и отказ сотрудником с причиной. Текущий API по-прежнему допускает прямой перевод в ready и создаёт упрощённый PDF; новый сценарий нельзя считать реализованным. Этот раздел не меняет фактический контракт маршрутов выше.
