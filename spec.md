## 1. Концепция и Ролевая модель (RBAC)
«Онлайн-деканат МУКПиД» — это единое цифровое пространство для организации учебного процесса, спроектированное по принципу **Mobile-First**. 

Система поддерживает роли student, teacher и staff. Исходные роли с жестким разделением прав доступа:
*   **🎓 Студент (`student`):** Имеет доступ строго к своим персональным данным (успеваемость, заявки, индивидуальные уведомления, обращения) и к общему расписанию своей учебной группы.
*   **Сотрудник (`staff`):** обрабатывает заявки всех студентов прототипа и изменяет расписание групп; не получает доступ к переписке и ведомостям преподавателя.
*   **👨‍🏫 Преподаватель (`teacher`):** Видит свое личное расписание занятий. Имеет доступ к электронным ведомостям только тех групп, в которых он ведет дисциплины. Обрабатывает входящие обращения от студентов.

**Авторизация:** JWT передаётся в HttpOnly-cookie, с Secure при HTTPS и SameSite=Lax. Токен содержит идентификатор пользователя, идентификатор сессии и срок действия; секрет подписи хранится только в серверном окружении. JWT не возвращается в JSON и не сохраняется в localStorage. При каждом защищённом запросе сервер проверяет подпись, срок токена и действующую сессию в базе. Выход отзывает сессию и очищает cookie, поэтому сохранённый токен сразу перестаёт работать. Срок сессии и JWT — 8 часов, автоматическое продление пока не предусматривается.

**Единый вход:** пользователь вводит email и пароль без выбора роли. Сервер определяет роль только по проверенной записи пользователя и возвращает её через `/api/auth/me`; домен email служит соглашением для демоаккаунтов, но не даёт прав сам по себе. Демоадреса: `student@edu.mukpid.ru`, `student2@edu.mukpid.ru`, `teacher@mukpid.ru`, `staff@staff.mukpid.ru`. Существующие демоаккаунты переходят на новые адреса с сохранением ID, паролей и связей. Адаптация формы входа и маршрутизации по роли выполняется во фронтенде отдельно.

**Изоляция данных:** текущий пользователь и актуальная роль определяются сервером через сессию и запись пользователя. JWT сам по себе не даёт доступ к чужим данным. Каждое чтение и изменение проверяет владельца объекта либо право преподавателя на конкретную дисциплину и группу. Без действующей авторизации возвращается 401; при отсутствии прав — 403. Проверки распространяются на все записи массового сохранения ведомости.

**Защита запросов:** сохраняются ограничение попыток входа и CSRF-защита для изменяющих запросов. Интерфейс и API работают на одном origin; контракт заголовков описывается в docs/api.md.

**Локальные демоаккаунты:** повторное заполнение базы не меняет пароли существующих пользователей. Для восстановления доступа к двум демонстрационным студентам предусмотрена отдельная локальная команда: она берёт новые пароли из окружения, проверяет их длину, обновляет только аккаунты `student@edu.mukpid.ru` и `student2@edu.mukpid.ru` с ролью `student` и отзывает их сессии. Аналогичная отдельная команда для преподавателя обновляет только `teacher@mukpid.ru` с ролью `teacher` из `SEED_TEACHER_PASSWORD` и отзывает его сессии. Обе команды запрещены в production.

**Демоданные для локальной проверки:** seed создаёт только вымышленные сведения: две группы с непересекающимся расписанием (у второй занятия сдвинуты на три часа), пять преподавателей и назначения по всем дисциплинам расписания, баллы обоих студентов, заявки, обращения (одно с ответом), разные материалы для каждой группы и уведомления. Повторный запуск дополняет отсутствующие записи, переносит только неизменённые старые занятия второй демогруппы и заменяет только прежний неизменённый шаблонный текст демоматериала; прочие пользовательские изменения и пароли сохраняются. Готовую справку с PDF демонстрируют через штатный сценарий сотрудника, а не подставляют как готовый файл в seed. Дополнительным преподавателям создаются случайные пароли без вывода в логи; вход в их аккаунты не входит в демосценарий.

**Время в интерфейсе:** текущая дата, часы, «сегодня», ближайшая пара и текущая неделя берутся из системных часов устройства и обновляются при открытой странице. Даты демонстрационных событий остаются абсолютными датами данных; для них нельзя показывать устаревшие относительные подписи. Вопрос о часовой зоне учебного расписания и серверном источнике времени остаётся открытым до подключения предметного API.

---

**Учебные дедлайны MVP:** преподаватель создаёт срок по своему назначению дисциплины и группы: заголовок 1–200 символов и дата/время в МСК, строго позже текущего момента. Он видит и удаляет только свои сроки; студент видит только сроки назначений своей группы. Ближайшие будущие сроки отображаются на главной студента по возрастанию даты. При создании студентам этой группы с включённой настройкой deadlines записывается уведомление. Удаление срока не удаляет уже отправленное уведомление. Срок задания не совпадает со служебным deadline заполнения ведомости.

**Объявления деканата MVP:** сотрудник публикует объявление с заголовком 1–200 символов и текстом 1–2000 символов для всех студентов либо для одной существующей группы. Студент видит на главной только общие объявления и объявления своей группы, новые первыми. Сотрудник видит и удаляет объявления в кабинете. При публикации подходящим студентам с включённой настройкой news создаётся уведомление; выключение настройки не скрывает само объявление. Преподаватель доступа к объявлениям не получает. Удаление не удаляет ранее созданные уведомления.

## 2. Схема базы данных (Ключевые сущности)

*   **`sessions` (Серверные сессии):** `token_hash` (SHA-256 от случайного jti JWT), `user_id`, `expires_at`, `created_at`; удаление записи отзывает доступ.
*   **`users` (Пользователи):** `id` (UUID), `email`, `password_hash`, `role` (student/teacher/staff), `full_name`, `faculty`, `group_id`, `department` (кафедра преподавателя). У студента group_id обязателен; у преподавателя может отсутствовать.
*   **`lessons` (Расписание):** `id` (UUID), `group_id`, `subject_id`, `teacher_id`, `room`, `type` (Лекция/Семинар/Практика), `starts_at`, `ends_at`, `change_type` (move/cancel), `change_note`.
*   **`grades` (Успеваемость):** `id` (UUID), `student_id`, `subject_id`, `score` (0-100), `semester`.
*   **`requests` (Заявки студентов):** `id` (UUID), `student_id`, `type` (Справка/Отпуск и т.д.), `purpose`, `comment`, `delivery` (pdf/office), `status` (submitted/in_progress/ready/issued/cancelled/rejected), `created_at`, `updated_at`.
*   **`inquiries` (Обращения):** `id` (UUID), `student_id`, `teacher_id`, `subject`, `text`, история в `inquiry_replies`, `status` (new/progress/closed).
*   **`notifications` (Уведомления):** `id` (UUID), `user_id`, `kind` (deadline/news/change/request), `title`, `text`, `is_read`, `created_at`.

## 3. REST API Endpoints

### Auth & User
*   `POST /api/auth/login` — Авторизация по email и паролю; устанавливает JWT в HttpOnly-cookie.
*   `POST /api/auth/logout` — Отзыв текущей сессии и очистка cookie; ответ 204.
*   `GET /api/auth/me` — Получение данных текущего профиля по токену.
*   `PATCH /api/user/prefs` — Обновление настроек уведомлений.

### Schedule & Grades
*   `GET /api/schedule` — Расписание для текущего пользователя (по группе или ID преподавателя).
*   `GET /api/grades` — Получение успеваемости студента.
*   `GET /api/gradebook/groups` — Список групп преподавателя для заполнения ведомости.
*   `PUT /api/gradebook/:id` — Массовое сохранение баллов преподавателем.

### Requests & Inquiries
*   `GET /api/requests` — Список заявок студента.
*   `POST /api/requests` — Создание новой заявки.
*   `PATCH /api/requests/:id/cancel` — Отмена заявки.
*   `GET /api/inquiries` — Входящие обращения (для преподавателя) или исходящие (для студента).
*   `POST /api/inquiries` — Создание обращения студентом.
*   `PATCH /api/inquiries/:id` — Ответ преподавателя на обращение и смена статуса.

### Заявки: первый рабочий этап

Форма передаёт `type` (study/order/leave/retake), обязательную `purpose` (1–500 символов после trim), `comment` (до 2000 символов) и `delivery` (pdf/office). Владелец определяется только сессией. Новая запись имеет статус submitted (Принята); сервер хранит purpose, delivery и даты создания/изменения. В одной транзакции создаётся персональное уведомление; его отображение ждёт API уведомлений.

Список содержит только заявки текущего студента, новые первыми. Фильтры интерфейса: все; в работе (submitted/in_progress); готовы (ready/issued). Отмена сохраняет запись со статусом cancelled, доступна только из submitted/in_progress; повторная отмена допустима. Для чужой заявки возвращается 403, для отсутствующей — 404, для недопустимого перехода — 409. Преподавателю раздел недоступен. Перевод заявки сотрудником и PDF описаны в разделе ниже. Старый rejected сохраняется как отдельное терминальное состояние.

### Notifications
*   `GET /api/notifications` — Лента уведомлений.
*   `PATCH /api/notifications/:id/read` — Отметка о прочтении.

## 4. Пользовательские сценарии (User Flows)

1.  **Подача заявки (Студент):** Переход в раздел «Заявки» $\rightarrow$ Выбор типа документа $\rightarrow$ Заполнение полей «Цель» и «Способ получения» $\rightarrow$ Система создает запись со статусом `Принята` и присылает уведомление.
2.  **Выставление оценок (Преподаватель):** Раздел «Ведомость» $\rightarrow$ Выбор дисциплины и группы $\rightarrow$ Ввод баллов (0-100) напротив ФИО студентов $\rightarrow$ Нажатие «Сохранить» $\rightarrow$ Обновление таблицы `grades`.
3.  **Обратная связь (Обращения):** Студент задает вопрос по курсовой через форму $\rightarrow$ Преподаватель видит бейдж с количеством новых вопросов $\rightarrow$ Открывает диалог, переводит статус в `В работе` и пишет ответ $\rightarrow$ Студент получает Push-уведомление.

## 5. ИИ-интеграции и "Фишки" (Масштаб нейротехнологий)

*   **ИИ-предиктор успеваемости:** На основе текущих баллов (`grades`) нейросеть формирует подсказки для студента (например: "Средний балл 68. Самый низкий результат: История России. Обратите внимание перед сессией").
*   **Умные уведомления (Smart Alerts):** ИИ автоматически генерирует персонализированные пуши на основе изменений в `lessons` (например, "Пара перенесена") и дедлайнов.
*   **Генерация PDF "на лету":** При статусе заявки `Готова`, бэкенд формирует демонстрационный PDF-бланк с ФИО студента, пометкой «Концепт для конкурса» и демонстрационной подписью.

## 6. Открытые вопросы перед реализацией разделов

- Ведомость: чтение, назначения и семестр определены ниже; административный экран управления назначениями остаётся открытым вопросом.
- Заявки: разграничение сотрудников по факультетам пока не предусмотрено; staff обрабатывает все заявки конкурсного прототипа.
- Уведомления: «прочитать все» и настройки определены ниже; настоящий Web Push/почта остаются за рамками этапа; дедлайны и объявления определены в разделе MVP выше.
- Время: учебные события задаются и показываются в Europe/Moscow, даты событий сохраняет сервер; синхронизация часов устройства с сервером остаётся открытым вопросом.
- Обращения: выбор по назначениям и студенческая форма добавлены; продолжение существующего диалога студентом остаётся отдельным этапом.
- PDF: юридически значимые документы и реальная подпись не входят в конкурсный прототип; реализуется только демонстрационный бланк.
- Демоаккаунты: сохранить минимум двух студентов с различными данными и добавить преподавателя; два аккаунта student/teacher из макета не заменяют двух студентов.


## Обработка заявок сотрудником и PDF

Роль `staff` (сотрудник деканата) видит все заявки и данные студента, необходимые для выдачи документа. Отдельный кабинет `/staff` содержит список, фильтр статуса и действия: submitted → in_progress → ready → issued. Отменённые/отклонённые записи терминальные. Для типов, кроме study, перевод в ready допустим и напрямую из submitted; для study целевой порядок обработки уточнён в следующем разделе; обратные переходы запрещены, повторный запрос текущего статуса допустим. Каждый переход сохраняет ID сотрудника и дату изменения; изменение состояния и уведомление студента выполняются атомарно. Предыдущая роль преподавателя не получает эти права.

GET /api/staff/requests и PATCH /api/staff/requests/:id/status доступны только staff. Студент не может менять статус через этот API. GET /api/requests/:id/pdf доступен владельцу-студенту, только для delivery=pdf и ready/issued; отсутствие прав 403, отсутствие записи 404, преждевременная выдача 409. Сотрудник скачивает тот же бланк через отдельный staff-маршрут. Повторное скачивание не меняет ready на issued; выдачу отмечает сотрудник явно.

PDF генерируется из сохранённой заявки и профиля студента, содержит тип документа, ФИО, группу, цель, номер заявки и дату готовности. Он содержит явные пометки «Концепт для конкурса», «Все данные вымышлены» и демонстрационную подпись без реального факсимиле. Для study это справка об обучении, для остальных типов - подтверждение обработки соответствующей заявки, а не вымышленный приказ или решение реального вуза. Готовый документ сохраняется в БД при переходе в ready, чтобы последующие изменения профиля не меняли выданный файл. Создание PDF должно успешно завершиться до фиксации ready.

Демоаккаунт сотрудника staff@staff.mukpid.ru создаётся seed с паролем SEED_STAFF_PASSWORD из окружения (не менее 12 символов); существующий пароль seed не меняет.

Для существующего демосотрудника отдельная локальная команда сброса меняет пароль staff@staff.mukpid.ru из SEED_STAFF_PASSWORD (12+ символов), проверяет роль staff и отзывает его сессии. В production сброс запрещён.


## Обработка справки об обучении (study): целевой сценарий

Статус: реализовано в ветке интеграции; подтверждение сценариев требует запуска тестов PostgreSQL. Предпросмотр предоставляется сотруднику через скачивание черновика.

### 1. Подача

Студент выбирает «Справка об обучении», вводит цель (обязательно), комментарий (необязательно) и способ получения (PDF/в деканате). Личные и учебные данные берутся из серверного профиля; их нельзя подменить в теле заявки. Результат — submitted («Принята»), номер заявки и время сервера. Вложения для обычной справки на этом этапе не требуются. Цель используется как указание получателя/назначения документа; произвольная цель не выбирает автоматически специальный шаблон, например для военкомата.

### 2. Проверка сотрудником

Сотрудник открывает карточку заявки и нажимает «Взять в работу»: submitted → in_progress. Карточка показывает ФИО, факультет, направление/программу, курс, группу, цель, комментарий, способ получения и дату подачи. Сотрудник проверяет сведения и подтверждает факт обучения; наличие роли student или группы само по себе не доказывает действующее обучение. Интеграции с реестром обучающихся сейчас нет: в прототипе используется явное подтверждение сотрудника «Сведения и факт обучения проверены» с сохранением его ID и времени.

Сервер проверяет наличие непустых ФИО, факультета, программы, группы, цели и положительного курса. При неполных данных подготовка документа блокируется с перечислением отсутствующих полей. Сотрудник не меняет профиль студента через заявку. Исправление профиля выполняется отдельным согласованным действием; до этого справка остаётся в работе либо отклоняется с понятной причиной.

### 3. Подготовка и просмотр

После проверки сотрудник нажимает «Подготовить справку». Сервер создаёт версию черновика из снимка данных; статус остаётся in_progress. Предпросмотр доступен только сотруднику и явно помечен «Черновик». Содержимое: название учебного заведения-прототипа, номер заявки, дата документа, ФИО, факультет, программа, курс, группа, подтверждение обучения, цель выдачи, демонстрационная подпись и пометки о конкурсном концепте. Паспорт, дата рождения, реквизиты приказа о зачислении и форма обучения не выдумываются: пока этих полей нет в проверенных данных, они не включаются.

Для готового бланка дата определяется сервером при подтверждении выпуска, отображение — МСК. Предпросмотр показывает проверяемые сведения; служебная пометка черновика и дата выпуска могут отличаться у окончательного файла. Набор данных и версия шаблона фиксируются. Перед подтверждением сервер повторно проверяет текущий статус и совпадение проверяемых данных с черновиком; если сведения изменились, старый черновик нельзя подтвердить, требуется новая подготовка и просмотр.

### 4. Подтверждение готовности

После просмотра сотрудник нажимает «Подтвердить готовность». Сервер допускает только переход in_progress → ready при наличии подтверждения проверки и актуального черновика. Прямой submitted → ready для study запрещён, в том числе при вызове API вручную. Финальный PDF создаётся из подтверждённого снимка данных, сохраняется вместе с ID сотрудника, временем подтверждения, версией шаблона и снимком сведений. Запись готовности, файла и уведомления студенту атомарна; при сбое генерации заявка остаётся в работе.

После ready содержимое документа неизменно. Изменение профиля или шаблона не меняет ранее сохранённый PDF. Для исправления выпущенного документа нужна новая заявка; отмена/подмена готового файла в этом этапе не предусмотрена.

### 5. Получение

Для PDF студент видит «Готова» и кнопку «Скачать справку»; доступ остаётся только у владельца и staff. Для получения в деканате студент видит «Готова к получению в деканате», а сотрудник скачивает и печатает тот же сохранённый бланк. Часы работы и адрес выдачи не выдумываются; они будут показаны после появления согласованных справочных данных.

ready → issued («Выдана») сотрудник подтверждает отдельно после выдачи. Скачивание не меняет статус автоматически. Повторное скачивание готового/выданного документа допустимо и возвращает сохранённый файл.

### 6. Отказ и отмена

Из submitted/in_progress сотрудник может отклонить заявку только с причиной (1–1000 символов после trim). Причина сохраняется и показывается студенту. Формулировка должна объяснять действие для повторной подачи: например, «Не заполнено направление подготовки в профиле. Обратитесь в учебный офис для исправления».

Студент может отменить submitted/in_progress; отмена делает черновик недоступным для выпуска. Отклонённая/отменённая заявка остаётся в истории, её нельзя сделать готовой. Причина отказа не публикуется другим студентам. Конкурирующие отмена, отказ и подтверждение готовности проверяются сервером атомарно; проигравший переход получает конфликт и актуальный статус.

В кабинете сотрудника отменённая заявка остаётся в общем списке с отметкой «Отменена» и без действий обработки; она не учитывается как новая или находящаяся в работе.

### 7. Критерии приёмки

- Справку нельзя сделать готовой без взятия в работу, проверки сведений и актуального предпросмотра, даже напрямую через API.
- Отсутствие обязательных учебных данных блокирует подготовку, без фиктивных подстановок.
- Студент не получает доступ к черновику или чужому файлу; преподаватель не получает права сотрудника.
- Изменение данных после подготовки требует повторного просмотра; скачивание после выпуска возвращает неизменный файл.
- После отказа студент видит причину; после отмены/отказа выпуск невозможен.
- Для обоих способов получения есть понятное конечное действие; ошибка генерации PDF не переводит заявку в ready.

Открытый вопрос для реального внедрения: источник подтверждения статуса обучающегося и требования к специальным формам справок. Прототип обрабатывает только обычную демонстрационную справку; реальные интеграции и специальные бланки требуют отдельных требований.

## Этап интеграции API (11 ноября 2026)

Этот раздел уточняет контракт реализации; прежние перечисления целевых маршрутов применяются с уточнениями ниже.

- Все кабинеты используют серверные данные, без подстановки предметных демоданных при ошибке. Ошибки, загрузка и пустые списки отображаются явно. Лента обновляется при возвращении во вкладку и раз в минуту; настоящий Web Push и почтовая доставка в этот этап не входят.
- Уведомления: GET /api/notifications, PATCH /api/notifications/:id/read, PATCH /api/notifications/read-all; GET/PATCH /api/user/prefs для deadlines/schedule/news. Служебные события заявок, обращений и оценок обязательны; настройка schedule отключает новые уведомления расписания. Историческое имя notifications.student_id пока сохраняется, но поле обозначает получателя users.id любой роли.
- Заявки: POST /api/staff/requests/:id/prepare с verified=true подтверждает проверку сотрудником и готовит снимок; POST /api/staff/requests/:id/preview с draftId возвращает черновой PDF и фиксирует его просмотр; PATCH статуса ready для study требует этот draftId и просмотр того же черновика. Изменение учебных сведений требует новой подготовки. Отказ через PATCH статуса rejected требует reason. Студенту возвращаются причина отказа, статус и готовый PDF, но не черновик. Для остальных типов сохраняется упрощённый выпуск. Отменённые/отклонённые записи остаются в истории.
- Расписание: GET /api/schedule?from=&to= возвращает только группу студента или занятия по teacher_id преподавателя. Сотрудник использует /api/staff/groups и /api/staff/groups/:id/lessons, POST занятий, PATCH/DELETE /api/staff/lessons/:id. DELETE означает отмену с сохранением записи. Время учебных событий — Europe/Moscow; на экранах явно указывается МСК. При создании/смене преподавателя требуется ID из GET /api/staff/teachers. Старые занятия без teacher_id доступны группе и сотруднику, но не присваиваются преподавателю по сходству ФИО. Новые пересечения группы, преподавателя или аудитории запрещены; параллельные изменения сериализуются в БД. CSV и повторения пока сохраняются поэлементно с явным отчётом о частичном результате; полноценная модель серии остаётся открытым вопросом.
- Учебные назначения: teaching_assignments связывает teacher, subject, group, semester (положительное число), form (Экзамен/Зачёт), deadline (необязательно). Начальное заполнение через seed; административный редактор назначений за рамками этапа. Преподаватель видит только свои назначения. GET /api/gradebook/groups возвращает ведомости со студентами и баллами; PUT /api/gradebook/:id принимает version и scores [{studentId, score}], score — целое 0–100 либо null (снять балл). Все записи проверяются и сохраняются одной транзакцией; устаревшая версия — 409, чужая группа/студент — 403. Истёкший срок блокирует изменение. GET /api/grades возвращает только собственные записи студента. Старую grades не удалять: новые баллы хранятся в grade_entries, связанные с назначениями.
- Обращения: GET /api/inquiries/teachers выдаёт назначения преподавателей для текущей группы студента; POST /api/inquiries {assignmentId, subject, text}; GET /api/inquiries — только собственные/адресованные текущему преподавателю; POST /api/inquiries/:id/replies {text} — ответ преподавателя; PATCH /api/inquiries/:id {status}. Единые статусы new/progress/closed. Ответов может быть несколько, каждый сохраняет автора и время; закрытое обращение нужно открыть перед ответом. Студент видит историю, отправляет новое обращение при необходимости. Staff не читает переписку. Тема 1–200, текст 1–5000 символов после trim.
- Учебные материалы: GET /api/materials и GET /api/materials/assignments доступны студенту (своей группы) и преподавателю (своих назначений). POST /api/materials {assignmentId,title,fileName,contentBase64} и DELETE /api/materials/:id — только преподаватель своего назначения. GET /api/materials/:id/file повторно проверяет доступ. Для прототипа допустимы PDF, TXT, PNG, JPG до 5 МиБ, сигнатура/кодировка проверяется; название 1–200. Выдача только attachment и nosniff; содержимое хранится в БД и не включается в списки. Файлы с персональными данными не использовать. Антивирус и внешнее файловое хранилище — отдельный этап.
- Изменения оценок и ответы создают персональные уведомления в той же транзакции. Ни один переданный клиентом userId, teacherId или studentId не заменяет проверку роли, сессии и объектных прав.

Открытые вопросы: полноценные серии расписания и атомарный CSV-импорт; SLA заявок в рабочих днях (текущую клиентскую метрику нельзя считать согласованным регламентом); администрирование учебных назначений; Web Push/почта; предметная адаптация прежних строк grades без автоматического угадывания баллов.
